# Project review — 2026-09-14

## Interpretation of the vision

This is a local collaboration transport for autonomous coding agents: peers find one
another by project-scoped names, send directly, and receive messages through their
harness even when idle. The important product promise is that agents can end their
turn and still participate in coordination. No model-managed inbox, polling loop, or
lead agent relaying messages is required.

The provider independence demonstrated so far is within OpenCode. Independence across
harnesses remains future work. File leases would make this useful for shared code
editing rather than just conversation, but reliable identity and delivery must come
first. Preserve the small agent-facing surface and the pure routing/adapter boundary.

## What exists and what works

- Four F# projects targeting .NET 10: domain, OpenCode adapter, daemon, and executable
  MCP shim. The shim starts the same executable in daemon mode.
- The domain represents identities, scopes, envelopes, routing decisions, parking,
  expiry, and session deletion without network or filesystem IO.
- The engine serialises state changes through a mailbox. Network delivery happens
  outside that mailbox, so a slow harness does not block all routing decisions.
- The adapter maps the two urgencies to synthetic `queue` and `steer`, reads SSE,
  and deduplicates cumulative tool-progress observations.
- The daemon correlates observed tool calls to MCP calls, scopes the roster, serves a
  private Unix socket, and expires parked messages every five seconds.
- The README records a successful bidirectional idle wake-up demo. That is valuable
  evidence of the core idea; it is not a repeatable integration test yet.

Both `dotnet build` and `dotnet build -c Release` passed with zero warnings/errors.
`dotnet test --no-restore` exits successfully, but there are no test projects or test
cases. The installed harness reports `opencode2 v0.0.0-beta-17519`, matching the
findings document, and `service status` reports a running local service. No live
agent sessions were prompted, interrupted, or changed during this review.

There was no AGENTS.md discovered in the project/parent search. The working tree was
clean before review. No implementation changes were made.

## Findings, in priority order

### 1. Attribution cannot uphold the identity guarantee under concurrency

`Attribution.fs` joins on bare tool name plus canonicalised arguments, oldest-first.
Two identical calls can be assigned to the wrong sessions. This affects **all three
verbs**, not just `roster`: identical `hello` names and identical `send` bodies are
possible. The README's assertion that only simultaneous cross-project rosters can
be swapped is incorrect.

A focused reproduction recorded identical sends for sessions A and B, then resolved
the call intended for B: it received A's endpoint. That demonstrates the ambiguity;
it does not measure its frequency in actual traffic.

The adapter also strips every MCP server prefix (`bareTool`) and does not filter the
observations to this server. Another server's `hello`, `roster`, or `send` can supply
a matching fact. The progress observation has a call identity for deduplication, but
that identity is not available on the shim side of the join.

This is a correctness boundary, not merely an ergonomic limitation: a send can acquire
the wrong sender or project. Prefer harness-supplied invocation metadata or a
harness integration that carries an opaque invocation identifier through both paths.
The model need not supply it. Establish what the harness can actually expose before
promising a fix. Detecting multiple candidate facts and refusing is useful mitigation,
but cannot prove safety when the second fact has not arrived yet.

### 2. Name ownership does not enforce the documented invariants

`Router.claim` always overwrites the registration for a name. A different live session
can claim it without a collision error, despite the design saying collisions error.
The intended restart behaviour needs to distinguish an unbound mailbox from a live
owner; unconditional replacement implements both as the same operation.

An endpoint can also claim several names. `boundTo` then selects the first matching
map entry rather than the most recently announced identity. `Router.observe` releases
only that one entry when the session is deleted, leaving another name falsely live.

Reproductions confirmed live-name replacement, two registrations for one endpoint,
and one live binding left after deleting that endpoint. Define repeat-hello,
rename, collision, and restart rules explicitly, then enforce one active name per
endpoint and one active endpoint per name.

### 3. Accepted parked mail can disappear, with a false success report

`Router.claim` removes the backlog from `Parked` before delivery. `Perform.Flush`
logs failures but returns no delivery outcomes and does not restore or retry mail.
The hello response nevertheless says all waiting messages have just been delivered.

A fake harness returning `SessionGone` confirmed that a failed flush produces no
outcomes and leaves the queue empty. A transient outage therefore loses messages
the sender was explicitly told not to resend.

Direct sends report failure, but a `SessionGone` fault does not release the stale
binding or park the message. Subsequent sends continue targeting the missing session.
Expiry removes mail before attempting its bounce too; failed bounces are only logged.

Introduce delivery acknowledgements back into the engine and retain ownership until
admission succeeds. Persistent storage alone would preserve this bug if it recorded
the current remove-before-IO transition.

### 4. Durability and reconnect reconciliation are absent

The registry and parked queue exist only in memory. Engine startup always uses
`RouterState.empty`. SQLite, durable pending delivery, and structured audit records
are not implemented. This is documented P2 scope, but it means the current system
does not yet satisfy the design's durability requirement.

The adapter reconnects its SSE stream, but there is no session/inbox reconciliation
route or recovery protocol. A missed deletion leaves a stale binding. Tool-progress
facts are non-durable and cannot simply be replayed, so reconnect does not recover
attribution for calls made during the gap. `ReadEvents` results are discarded by the
pump; repeated discovery/auth/HTTP failures have no useful connection-state log.

Use a durable outbox with stable message IDs and explicit admission results. Establish
the harness's idempotency/reconciliation capabilities before choosing retry semantics:
an HTTP timeout may mean admission succeeded but its response was lost. Blind retry
can duplicate messages. Admission to the harness is also distinct from model processing.

### 5. Several startup and transport paths can hang or conceal failure

- Discovery calls stdout `ReadToEnd`, then stderr `ReadToEnd`, **before** its five-second
  `WaitForExit`. A hung subprocess can block before the timeout; full stderr can also
  deadlock with stdout reading. Read both asynchronously under a deadline and kill
  the subprocess on timeout.
- The shim has no deadline for reading a daemon answer. Since MCP requests are handled
  synchronously, one stuck call also blocks later pings and calls on the shared shim.
- Socket readiness is not SSE readiness. The daemon binds before initiating the
  subscription, and `Observe()` starts an asynchronous pump without awaiting a
  connection. Warming the shim cannot guarantee the first attribution event is seen.
- Failed connection attempts allocate sockets without disposing them. Long outages
  repeatedly exercise this path.
- Malformed MCP JSON is logged without a JSON-RPC error response. Protocol negotiation
  echoes any requested version. These paths deserve small protocol tests despite the
  claim that the shim contains nothing worth testing.

These are source-inspection findings; the subprocess hang and transport deadline
paths were not exercised against the live service.

### 6. Smaller identity and queue inconsistencies

`Scope.key` lowercases paths unconditionally. Distinct directories `/project/A` and
`/project/a` become one namespace on case-sensitive filesystems; this was reproduced.
Trailing-slash/lowercase normalization also does not resolve path aliases or symlinks.
Choose a documented project identity rule appropriate to supported platforms.

`AgentName.create` trims input despite the explicit promise never to rewrite names.
Either reject surrounding whitespace or document normalization.

Claim flushes expired mail if the expiry timer has not run yet. A claim at 100 seconds
flushed mail with a 90-second deadline in a reproduction. Deadline handling should
be part of the claim decision, not depend on timer scheduling.

The bounded adapter dedupe key omits endpoint identity. If assistant/call identifiers
are reused across sessions, distinct calls would be suppressed. That scenario was not
established against the installed harness; including the endpoint is inexpensive.

Delivery effects from separate requests can interleave after the engine has serialised
their decisions. Only an individual flush is delivered sequentially. Define whether
per-mailbox ordering is promised, and enforce it if required.

## Missing work that is already acknowledged

P2: persistence, reconciliation, meaningful audit records, rate limits, duplicate-message
suppression, queue bounds, interrupt budgets, and activity-aware roster cleanup.
P3: Claude Code transport, file leases, and permission isolation.

Synthetic provenance is useful, but does not itself constrain what a privileged
recipient can do in response to peer text. Permission isolation remains an unresolved
policy/integration problem; a router treating bodies as opaque cannot infer arbitrary
requested capabilities. Resolve the precise enforceable requirement before claiming
that the planned guard covers it.

There is also no automated test suite, CI configuration, SDK pin, repeatable demo
harness, publish/install path, or daemon status/restart/version workflow. A long-lived
daemon can keep running old code after rebuilding the executable. Operational tooling
will matter once this is used regularly.

## Recommended next sequence

1. **Make the P1 contract trustworthy.** Specify and test identity ownership; address
   attribution with a concrete harness investigation; fix failed-flush ownership and
   false success wording; enforce deadlines; make startup/connection failures visible.
   Correct the README's attribution and completeness claims. Preserve the three tools.
2. **Implement delivery reliability as a state machine.** Specify pending, admitted,
   retryable, expired, and permanently failed outcomes before writing SQLite code.
   Persist registry/outbox/audit changes together, feed delivery results back into the
   engine, and reconcile after daemon/harness restarts. Decide how ambiguous admissions
   are handled. Avoid an unsupported exactly-once promise.
3. **Add bounded operation.** Queue depth/body limits, pair rate limits, message dedupe,
   and interrupt budgets. Add roster activity policy and minimal daemon diagnostics.
4. **Prove repeatable behaviour.** Unit tests for routing and attribution, fake HTTP/SSE
   integration tests for disconnects and failures, and an isolated two-session smoke
   test for idle wake-up and busy queue/steer delivery. Run the deterministic suite in CI.
5. **Extend across harnesses, then coordinate edits.** Build the Claude Code adapter
   against a verified current transport contract. Demonstrate a bidirectional
   cross-harness exchange before adding leases. Define lease expiry, ownership, and
   conflict behaviour separately from chat; advisory leases need explicit cooperation
   or an enforcement integration.

The best immediate milestone is: two named peers can send, stop, restart, and resume
without messages silently disappearing or identities changing. That advances the
original vision more than another provider demo or a larger tool surface would.
