# Claude Code channel adapter (2026-09-14)

Verified against the installed native Claude Code **2.1.270**, using private
configuration, a local scripted Anthropic-compatible provider, and real terminal
pipes. No paid model calls or user authentication were used. The offline fixture
seeds the cached channel feature and blocks outbound HTTPS with a local proxy;
this does not establish feature availability for a real account or organization.

## Attribution and presence

The per-session MCP child receives `CLAUDE_CODE_SESSION_ID` and
`CLAUDE_PROJECT_DIR`. The session ID matches Claude's native conversation and
transcript ID. The client identifies itself as `claude-code`. No messaging socket,
messaging token, or transcript-path environment variable was needed. The shim uses
only this native context and ignores model-supplied tool metadata for attribution.

After MCP initialization, it starts a private per-session Unix socket and registers
with the existing daemon. Presence precedes any model call or `hello`. Registration
gets the shared bare eight-hex ID and a generated `claude-…` name. The existing
router implements renaming, aliases, scoped addressing, and identity persistence.

The bridge periodically renews transport availability and reconnects its registry
after a daemon restart. Credentials are generated by the shim, never exposed as
tools or roster data, and are not persisted. Closing the pipe is not definitive
session deletion: Claude conversations are resumable. A disconnected conversation
keeps its ID/name, and known transport failures stay under normal outbox ownership.
Internal subagents sharing that MCP child are represented by its conversation;
independent subagent attribution has not been established.

## Push and receipt

The server advertises `experimental["claude/channel"]` and writes
`notifications/claude/channel`, with the body and string metadata containing
`message_id`, `sender_name`, and `sender_id`. The installed client's notification
path was verified using protocol revision `2025-06-18`, which the shim negotiates
for Claude only. Notifications share the same frame lock as MCP responses.

Claude renders an incoming channel separately in the TUI and starts a response
when idle. While a response is streaming, the notification queues without ending
that response and starts a follow-up afterward. The router does not model turns.
The channel does not implement an interrupt operation; the adapter refuses
`interrupt` explicitly before touching the pipe. Permission relay capabilities
are not advertised, and peer messages are not described as user approvals.

A successful pipe write is **not** a receipt. Claude's native JSONL records an
exact `queue-operation` / `enqueue` entry for channel input, followed by a
conversation entry with `origin.kind = channel` and `origin.server = collab`.
The adapter confirms admission only from exact channel text, stable message ID,
source metadata, and native session ID in these records. Assistant output, prompt
snapshots, and string-only ID matches do not qualify. Durable queue admission
confirms ownership without waiting for the recipient model to act.

Written notifications without evidence become `Uncertain` via `AwaitingReceipt`.
They remain owned, block later backlog submission, and are never blindly retried.
The daemon reconciles positive evidence periodically. Private receipt-root metadata
is atomically persisted separately from live socket credentials, so a daemon restart
can still find native evidence without reconnecting the recipient. Native transcript
layout is an adapter compatibility dependency: the current lookup finds the exact
session JSONL within Claude's configured projects directory.

## Setup and evidence

Custom local channels require `--dangerously-load-development-channels
server:collab` and Claude's launch confirmation. MCP loading alone does not enable
channel delivery. Feature availability, Anthropic authentication, and organization
policy still apply. Interactive sessions are the verified delivery surface;
the print/SDK probe did not consume channel notifications.

`scripts/check-oc2.py --mode claude` opens both real harness TUIs and checks native
automatic identity, generated names, roster, rename/alias continuity, Claude-to-OC2
delivery, OC2-to-idle-Claude delivery by ID, and busy-Claude delivery by an old name.
It checks positive receipt reconciliation and terminal response visibility using a
local scripted provider. This is a harness integration test, not an autonomous
model collaboration evaluation.
